# AI開発・コーディング指示書 (INSTRUCTIONS.md) - common_lib

[English](../en/INSTRUCTIONS.md) | **日本語版**

本ドキュメントは、AIエージェントおよび開発者が `common_lib` プロジェクトに対してコードの追加・修正を行う際に遵守すべきコーディング規約、実装方針、および作業時のルールについて定めたものです。

---

## 1. 命名規則

Rustの標準的な命名規則（Idiomatic Rust Style）に従います。

- **変数・関数・マクロ**: スネークケース (`snake_case`)
- **型・構造体・列挙型・トレイト**: パスカルケース (`PascalCase`)
- **定数・スタティック変数**: スクリーミングスネークケース (`SCREAMING_SNAKE_CASE`)
- **ファイル名・ディレクトリ名**:
  - ソースコードはスネークケース (`snake_case.rs`)
  - ドキュメントファイルは大文字のスネークケース (`DOC_NAME.md`)

---

## 2. エラーハンドリング方針

- **パニック（`panic!`, `unwrap`）を避けることを最優先**とし、エラーは必ず戻り値（`Result`）として返却して呼び出し側で処理させます。
- **共通エラー型の使用**: クレート共通のエラー型 `crate::Error` (列挙型) および結果型の別名 `crate::Result<T>` を使用します。

---

## 3. コンポーネントやモジュールの分割基準

- **OS / プラットフォーム依存の機能**: `src/desktop.rs` に配置します。Windows 以外のOSや、フィーチャーフラグがオフのビルド環境でもコンパイルエラーを起こさないよう、同名のダミー構造体およびダミー関数（スタブ）を常に提供してください。
- **プラットフォーム非依存の純粋ロジック**: `src/text.rs` に配置します。
- **ファイル規模の上限と分割推奨 (1000行制限)**: 1つのソースコードファイル（`.rs`）が 1,000 行を超えた場合は、保守性や可読性の低下を防ぐため、機能やサブモジュールごとにファイルを分割・リファクタリングすることを推奨します。

## 5. 品質管理・検証プロセス (モジュール化退避)

- **ユニットテストの追加・拡充**: 新機能追加やコアロジック変更時は `src/` 内のモジュールテスト等を追加・拡張。
- **ローカル事前検証**: 報告前に以下コマンドを順次実行し、エラー・警告ゼロを確認。
  1. `cargo test` （テスト合格）
  2. `cargo clippy --all-targets -- -D warnings` （Clippy警告ゼロ）
  3. `cargo fmt --check` （フォーマット適合）
  4. `cargo doc --no-deps --document-private-items` （Rustdocビルドエラー・警告ゼロ）
